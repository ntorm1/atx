## Important

**R1 — Task5 measurement commands can audit the wrong producer.** Matrix D09 uses `fund_validate balance --stages fundamentals_v11`; C04 uses `fund_validate coverage exit --stages fundamentals_v11`. `fund_validate.run` takes `_stage()` from `ATX_FUND_STAGE`; `--stages` controls only ttm_gaps/exit, not coverage/balance/benchmark/cutoff. Matrix environment does not set ATX_FUND_STAGE. Thus D09 and C04 coverage can read the legacy/default producer while appearing to measure v11. Bind the environment explicitly (or use an explicit stage selector implementation) and pin the actual versioned standardized/ratio stage in downstream commands. This is not a changed numerical threshold, but makes the declared commands insufficient to enforce it. The revised Task5 out_path isolates v11 evidence only when that environment is actually selected.

**R2 — Owner profitability/growth acceptance is not represented explicitly.** C04 pins original117-item/exit targets correctly, and C08 mentions owner families generally, but no executable/readiness row requires the owner primitive→formula→gold matrix or every requested family's yearly coverage in all three universes. Missing are explicit quarter-YoY/annual/TTM and margin/profitability changes, per-share/dilution history, sector applicability, currency/restatement/duration/basis qualification and associated quality/null reasons. Owner-addendum obligations also require adding ownership-breadth change(+), split-adjusted ownership change(+), operating profitability(+) and annual asset growth(-) to the committed preregistered config before first returns; P01/P02 do not identify these additions or registry deduplication. Authority links and 'plus owner families' leave these acceptance requirements unenforceable at row level. Add dedicated OPEN requirements/evidence/config checks; do not invent numeric coverage thresholds where the owner required measurement/disclosure only.

**R3 — Consumer contract omits strict role recipe restrictions that affect honest integration.** It correctly declares runtime acceptance pending and unknown-subcommand failure, and its extra-field64/<f8/date-major contract matches inspected code. But `strategy_data.cpp:84–118` additionally requires exact close/volume/clock recipes, `common_stock_verified=false`, `historical_vintage_verified=false`, at least383warmup rows, and a prior63-session ADV top-N membership recipe with price>$5, ADV>$5m, lag1 and completeness rules. These are absent from consumer-contract-v1.json. In particular the loader's required research membership is not identical to golden all_common membership. Record both domains explicitly: preserve the complete all_common golden panel, export an honest role-specific membership/basis contract, and avoid presenting the loader's fixed false qualification flags as production source certification. A compatible binary/adapter still needs actual acceptance; emptying/changing metadata to fit the existing loader cannot establish source truth.
