# CompanyFacts archive throughput: static audit

Scope: `feat/tier1-parity` at `380cc73f`; source reading only. No production code, runtime, database, test, network, or job changes. The supplied guarded observations are 9,440 targets / 39.4 million rows in six minutes for archive12; 10,800 verified members of 20,390 in eight minutes on resume; and 16 newly loaded CIKs / 45,185 attempted rows in 77 seconds before external host memory crossed the guard threshold. These are aggregate observations, not phase timings. The host stop does not establish a loader memory leak or a per-CIK throughput regression.

## What repeats

- VR1 already addressed the avoidable verified-prefix recycle pattern. Verified members retain their candidate cleanup transaction, but now use a separate 100-member recycle counter; raw replacements still recycle after ten (`fundamentals.py:1157-1185`, `verified-resume-recycling-root-verification.md`). Do not reopen that change based on the current aggregate timings.
- Every newly parsed CIK passes ZIP read/JSON decode, normalization, and per-fact identifier resolution (`fundamentals.py:1201-1261`). Normalization builds both fact and point Python row lists and DataFrames (`:661-737`). The resolver submits distinct CIK/availability pairs to DuckDB, then loops through each fact with pandas scalar `.at` reads/writes (`:418-550`). This is issuer-sized work and could matter for large members, but the 77-second interval does not isolate it.
- Each successful replacement starts one transaction, creates three issuer-key temporary tables, deletes matching `fundamental_points`, deletes old raw facts, reconciles candidates, inserts both frames, records the receipt, and commits (`fundamentals.py:1421-1489`). The point DELETE joins the full points table to issuer keys (`:1464-1475`); the source does not prove DuckDB scans the full table for every CIK. The old raw-key selection and raw DELETE use the once-per-load exact-CIK spelling inventory (`:1025-1042`, `:1274-1283`, `:1429-1437`, `:1477-1479`), which removed the previously identified repeated regex/cast selection. The inventory itself is a single distinct scan, not per-CIK work.
- Empty replay members intentionally take the replacement path to remove stale owned rows and write an empty receipt. Verified loaded members do not parse/reinsert facts or points (`fundamentals.py:1167-1190`). Full archive hashing and the resume multiset proof occur before the loop (`:1118-1148`, `_companyfacts_resume.py:150-275`); neither can be assigned to the 16-new-CIK interval without timestamps.

## Decision

There is no statically proven redundant full-table operation left that warrants a production rewrite now. Retain the current replacement, proof, and recycle semantics. The only bounded next task with a concrete benefit is focused **aggregate phase timing during an already necessary guarded continuation**, if host headroom is stable: at the existing progress cadence, record elapsed time and row count for ZIP/normalize, identifier resolution, replacement transaction, and recycle; within replacement, separate point DELETE, raw DELETE, and frame inserts. Keep timers outside per-row loops and avoid payload or SQL result capture. This would distinguish a point-table cost from issuer-sized Python and insertion costs before choosing any optimization. It is measurement guidance, not a request for a separate benchmark or test loop. The current host-memory bursts remain the immediate constraint on completing the full production fundamentals load.

## 512 MB configuration check

Static conclusion: no code-level minimum or resume-identity blocker was found for passing `--memory-limit 512MB` to the next activation continuation while retaining one thread, the same process guard, archive, scope, and proof. Activation accepts any nonblank memory-limit string and configures the DuckDB session before stages run (`activation.py:212-247`, `:1127-1133`, `:1226-1231`; `cli.py:77-92`). The configured string is stored on `DuckDBStore`; CompanyFacts' post-proof and cadence recycling calls `reopen_companyfacts_store`, which requires a configured persistent store, then `close()`/`reopen()` reapplies that same limit and thread count (`_companyfacts_resume.py:278-290`; `connection.py:105-134`). Failed-connection ledger recovery also uses the recorded limit (`connection.py:136-165`). `check_publication_session` checks temporary relation ownership and configured-store eligibility, with no numerical minimum (`_fundamental_publication.py:24-49`).

The resume lineage compares archive path, selector, full-window/replacement settings, as-of date, universe, and concept allowlist; it does not compare memory or thread settings (`_companyfacts_resume.py:60-104`). Activation's resume-plan check likewise has no memory equality test (`activation.py:1085-1095`). This is permission from the code to *try* the lower query budget, not evidence that the 47.9-million-row fingerprint proof, point deletion, checkpoint, or inserts will complete under it, nor that process private bytes will fall proportionally. A DuckDB allocation or spill failure would be a runtime result for the root controller to handle under the unchanged guard.
