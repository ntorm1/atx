# Fundamentals activation runtime audit

Static source review, 2026-09-20, `feat/tier1-parity`. This audit opened no database, ran no tests or Python imports/probes, and made no code changes. Graph tools were unavailable; discovery used source-only `rg` and PowerShell reads. The controller owns the guarded source prepass and subsequent production measurements.

**Result:** no remaining whole-fact-table Python/DataFrame materialization was found in the seven requested activation paths. The concrete remaining exposure is full-universe SQL computation and indexed publication in single transactions, especially the fact-revision rebuild and standardization. These operations necessarily cover the full scope; source inspection does **not** establish that they exceed the 1 GB DuckDB limit or 3 GiB process-tree guard. Run the guarded ladder and use the actual failing operation to select a bounded repair. Do not remove indexes or change publication architecture speculatively.

The historical 31,590,760 raw-fact count in `atx-db/docs/TIER1_ACTIVATION_STATUS.md:45` predates the archive-wide prepass. It motivates scale scrutiny, but is not a current row count or a memory estimate for these stages.

## Failure-triggered repair briefs and safe partition boundaries

None of these briefs authorizes a migration, registry change, activation edit, index removal, or live workload. They are possible bounded implementation tasks after the controller records a real stage failure.

1. **If revisions or statement-point creation fails:** narrow work by complete `security_id` scopes, applying the same predicate to input selection and output replacement. Revision groups include security/source/taxonomy/concept/unit/period; keep all revisions and their current ordering within each group. Revision-only `concepts` filtering already exists and is semantically separable, but a popular concept can still be very large. Statement-point generation must keep all competing concepts for a canonical metric together (`fundamental_statements.py:1131–1147`). Naively looping its `concepts` option can change the winner or collide on the canonical point ID. Include security-scoped REIT inputs and derived outputs; do not skip that insert. Build the partition inventory from source **and existing destination** identities so source disappearance still clears stale output.

2. **If periods or TTM fails:** keep each security's reporting history together. Periods requires all metric contributions per accession/period, all period revisions, and that security's complete eligible Item 2.02 8-K candidates for the existing RDQ selection (`fundamental_statements.py:1384–1416`). Both TTM engines can partition by security and, independently, canonical metric, while retaining all units/sources/revisions and relevant YTD predecessors. The existing ordinary-TTM `canonical_metrics` scope already filters both DELETE and source scan (`1496–1505`, `1582`). Do not split by arbitrary calendar date, accession, or row count: quarter derivation, PIT visibility, and revision sequencing cross those boundaries. Keep the current 400-day clauses and all method/tie-break rules unchanged.

3. **If standardization fails:** scope every candidate/quarter/event relation to complete security histories before the expensive work, then publish the same scope. Combination `visible_inputs` expands events against earlier available inputs (`_standardization_set_based.py:655–714`); quarter event reconstruction has a similar pattern (`394–430`). These are issuer-local joins, potentially quadratic in revision count within a logical period, not cross-issuer peer computations. Preserve all rule inputs, source precedence, event clocks, revision ordering, hashes, and exception rows. Existing symbol filtering is not automatically a safe security partition: aliases can divide one security's history, and blank-symbol rows need explicit coverage. Prefer a security-ID scope, or first prove each symbol scope contains complete security histories. Dropping temporary relations after their last consumer can reduce spill footprint but does not bound the final indexed publication.

4. **If calendarization fails:** distinguish map computation from map publication and calendar TTM. The map oracle already has a fixed Python-row bound; another pandas rewrite is unwarranted. Its fiscal-year inference needs all annual periods per `(upstream source, security_id)` before row batching (`calendarization.py:295–327`). A security-scoped calendar-TTM task must retain that security's full mapping and quarterly/YTD history. Coverage aggregates must be recomputed over the complete successfully published surface, not summed carelessly from overlapping batches.

5. **If an existing reconciliation or derived-metrics batch fails:** first reduce that existing scope rather than replace its engine. More reconciliation shards is supported; retry with changed shard boundaries must cover the entire intended universe, not reuse an old `start-shard` position as though boundaries were unchanged. A derived-metrics task can use a smaller `DerivedMetricsOptions.batch_size` and retain all metrics in topological order within the transaction. Never split dependency chains into inconsistent partial refreshes. Both scopes retain full security history. A single unusually large issuer can still require further work; fixed security count is not a hard byte limit.

None of the reviewed numerical computations needs cross-security peer history. Shared dictionaries/rules remain globally available. Calendar inference and RDQ lookup need complete issuer history; standardization and reconciliation need complete issuer event/input histories; derived metrics need the dense complete quarter grid and metric dependencies. These are the semantic boundaries that a bounded repair must preserve.

**Publication caveat:** batching SQL inside the existing outer full-universe transaction does not bound the transaction's complete write/index scope. Committing each security partition preserves PIT calculations but changes all-or-nothing publication into a sequence of scoped publications. If whole-stage atomic visibility remains required, use the measured failure to design a separately reviewed publication solution; an unindexed staging table followed by one giant indexed INSERT merely moves the same potential failure to the end. This audit does not propose that architectural change now.

## Failure and retry behavior in the current code

`DuckDBStore.transaction` explicitly rolls back ordinary exceptions (`connection.py:270–279`). On that path:

- Revisions, statement points, periods, ordinary TTM, calendar map, and calendar TTM each retain their own preceding output if their individual DELETE/INSERT transaction fails. Unscoped revisions/points/periods/TTM replace all sources; calendar `options.source` identifies the output source, not an upstream-input restriction. Scoped concept/metric retries leave other output scopes intact.
- `statement_points` is three separately committed refreshes: successful catalog/revisions can coexist with older points after a later failure. Calendarization similarly can leave a newer map with older calendar TTM/coverage. Neither activation stage is one atomic unit.
- Standardization builds temporary inputs before touching output. Its output-source DELETE and both inserts share a transaction; an ordinary publication exception preserves older standardized/exception rows. The build record is separately marked failed. With symbols, only that output-source/symbol scope is replaced.
- Reconciliation preserves the failing shard's preceding output if its publication transaction fails; earlier successful shards remain committed. Derived metrics has the same per-security-batch behavior, scoped by output source and optionally the expanded metric dependency closure. A failed overall stage can therefore contain completed earlier scopes.

A process-tree termination is not the Python exception path. Post-termination recovery and output preservation require the controller's normal reopen/measurement evidence; this static review cannot certify them. The guarded ladder should record the failing function/SQL phase so a retry repairs the necessary scope and revalidates downstream consistency.
