# FQ2 fundamental evaluation contract: static audit

Read-only code audit of the in-progress FQ1 panel and existing return/evaluation paths. No database was opened and no runtime claim is made.

## Actual source surfaces

- `migrations/bodies_0324.py::_fundamental_signal_panel` defines `fundamental_signal_runs` (`status`, `spec_json`, `spec_sha256`, `definitions_json`, `definitions_sha256`, `query_version`, `source_ids_json`, `calendar_sha256`, `start_date`, `end_date`, `as_of_date`, `run_at`, `decision_policy`, `panel_sha256`, blockers), frozen `fundamental_signal_definitions`, daily `fundamental_signal_values` (`signal_id`, `decision_date`, `security_id`, `decision_at`, `entry_date`, `score`, `eligible`, `reason`, input clocks), term-level inputs/proofs, and per-signal/date coverage. No FQ2 result tables yet.
- `fundamental_signal_research.py::build_fundamental_signal_panel` finishes a run as `complete` only with sessions and at least one eligible score. The digest is SHA256 of canonical `[spec SHA, definitions SHA, calendar SHA, values SHA, inputs SHA, coverage SHA, proofs SHA]`; row digests use ordered SQL streams and canonical row JSON. An evaluator must recompute this exact recipe, compare `panel_sha256`, verify `spec_sha256`/`definitions_sha256`, and reject missing/extra/duplicate rows, changed definitions and noncomplete runs. Merely checking the manifest's stored digest is insufficient. `default_signals()` declares four single factors plus `fundamental_rank_mix`; custom runs allow 1..32 canonical signal specs, so family size comes from the frozen definitions for that run.
- `_sessions` uses observed `market_daily_metrics` dates with source `atx-db daily market panel v1`; entry is the next observed date, and FQ1 sets `decision_at` to 22:00 UTC. `_stage_cohort` selects dated, visible `universe_us_listed_membership` and CIK history. `_publish_signal` persists both eligible and excluded values and keeps score ties for rank transforms. The FQ1 fields do **not** include price, liquidity, or a forward-label ID.
- `delisting.py::SurvivorshipSafeForwardReturnOptions` defaults to source `atx_forward_returns_survivorship_safe_v1` and `price_basis='adjusted_close'`; `close` is an explicit compatibility option. `refresh_survivorship_safe_forward_returns` calls `_forward_return_publication.py::refresh_forward_return_publication` with observed XNYS bar-calendar sessions and the standard horizons. The publisher selects one available `equity_daily_bars` row per security/date, uses the selected adjusted price with no raw-close fallback, and produces `forward_return`, `raw_forward_return`, `terminal_return`, `is_delisted_in_horizon`, `terminal_return_source`, `return_observation_id`, `forward_end_date`, `available_at`, `run_id`. Terminal policy uses latest available `delisting_terminal_returns` event, last positive price strictly before delist, and geometric stitching; invalid chosen terminal suppresses the crossing label. The table's `horizon_days` is measured from **its own `as_of_date`**, so FQ2 must join on FQ1 **entry_date** and exact security/horizon, then check end date against the expected 5/21/63-th observed session after entry. It must not join on decision date.
- `migrations/bodies_0185_0188.py` defines the forward table and a `v_forward_returns_survivorship_safe` view filtered only by `is_latest_revision`. `_forward_return_publication.py` replaces all rows of one source through a validated shadow; its stable ID is SHA256 of source/security/date/horizon. `run_id` is nullable, `source_loaded_at` is a load clock, and **no stored `price_basis`, price-source digest, calendar digest, or publication manifest exists on the labels**. `migrations/bodies_0312.py` documents the corrected adjusted-close default and explicitly says economic adjustments and historical vintages still need independent validation. Catalog metadata is a default description, not row-level proof.
- `custom_features.py::evaluate_custom_features` is the closest evaluator: SQL ranks before labels, next-session entry, exact 5/21/63 label keys, latest revision by `(available_at,source_loaded_at,forward_return_id)` within cutoff, expected end-date/terminal checks, chronological splits with crossing purge and 63-session embargo, per-decile coverage and calendar-aware HAC. Its current prerequisite is only horizon presence; its configuration says the operator must supply the corrected adjusted panel. FQ2 should not treat this as price-basis verification. `calendar_hac_statistics` is pure and reusable for daily spread series; it preserves actual session gaps, uses Bartlett lag `horizon-1`, and returns no p-value for insufficient/degenerate samples. `holm_eight` is hard-coded to eight CF1 features; FQ2 needs a family-size-parameterized equivalent that retains missing hypotheses as p=1 in the ordered family and reports their adjusted p as null.

## Minimum FQ2 evaluation gate and output

1. Accept an explicit completed FQ1 `build_run_id`, an explicit evaluation `run_id`, label source and evaluation cutoff. Recompute the FQ1 digest from the frozen run tables with its exact canonicalization and ordering; check definitions, coverage grain, one score row per signal/date/security, and every requested decision session, including excluded/empty states. Persist the build digest and evaluation configuration in an immutable evaluation manifest. Do not evaluate a live panel that fails revalidation.
2. Require a verifiable label publication identity that records source, `price_basis='adjusted_close'`, input bar source/digest or comparable reproducible publication proof, observation cutoff, calendar source/digest, publisher version and published-row digest/count. Revalidate the current labels against it before scoring. The existing table cannot prove adjusted provenance: `run_id`, source name, catalog prose, and `raw_forward_return` do not identify basis. If FQ2 cannot obtain a new label manifest, fail closed with an explicit `unverified_label_price_basis` result; do not call horizon presence or default options proof. Recomputing the selected bar/terminal legs under the adjusted option is an alternative only if bounded and exact, including revision selection; economic correctness of vendor adjustments remains a separate blocker.
3. Construct ranks/deciles from **eligible, finite FQ1 scores at each decision date before joining outcomes**. Use deterministic `security_id` tie-breaking for allocation but report tied-score/constant-cohort counts, small cohorts and per-decile membership; avoid asserting economic separation when a cut splits equal scores. One date's score distribution cannot be altered by missing labels. For every 5/21/63 horizon, retain missing, invalid, terminal observed/policy and available label counts and coverage by date/decile; do not silently survivor-filter. Join source/security/entry/horizon, choose latest revision **as of evaluation cutoff before validation**, require finite return >= -1, matching expected end date, valid terminal provenance and outcome availability; label `available_at` is a realized outcome clock, not a decision-time input.
4. Use a fixed, predeclared chronological train/validation/holdout boundary and record it in the manifest. Exclude a date if its endpoint crosses its split boundary; apply 63 observed sessions of embargo at each later split. Use the same calendar for FQ1 entry and endpoint validation or explicitly reject calendar mismatch. Compute equal-weight daily Q10-Q1 spreads from decile mean outcomes and inference on the daily series with `calendar_hac_statistics`; do not compress skipped dates. Treat 21 sessions as primary and 5/63 as secondary. Predeclare the whole frozen signal family, including zero-coverage/untestable signals, in Holm correction for each primary split; carry null p-values and explicit failure statuses. Preserve all attempted signal/horizon/split rows, economic net cost scenarios, year-by-year stability, coverage and production blockers. A positive score alone is not a portfolio PnL claim.
5. Keep all large membership/rank/label/decile joins in DuckDB with bounded date or partition stages, fixed memory/thread limits and only aggregate daily spread rows crossing into Python. FQ1 already commits one session at a time under 256 MB/one thread; CF1's evaluator materializes broad temp tables, so copy its statistical rules rather than assuming its execution path fits FQ2's memory envelope.

## Price/liquidity cohort availability

`migrations/bodies_0302.py` gives `market_daily_metrics.close`, `adj_close`, `volume`, `available_at` and `trade_date`; raw bars also supply `close`, `volume`, `adjusted_close`, `available_at`. `migrations/bodies_0313.py` and `custom_features.py::refresh_custom_features` already calculate prior-session `raw_close`, `dollar_volume_mean_63`, and `valid_dollar_volume_63`, with the CF1 rule `raw_close>=5 AND valid_dollar_volume_63>=50 AND dollar_volume_mean_63>=1,000,000`. Those fields are **not** in FQ1 `fundamental_signal_values` or its manifest, and the CF1 table has a distinct build/source and cohort provenance. An FQ2 standard price/liquidity screen therefore needs an explicit point-in-time join to the prior observed session's qualified market/bar observations, or a separately verified CF1 run. Apply stored `available_at<=decision_at`, exact 63-session windows and at least 50 valid dollar-volume observations; freeze the cohort and record exclusions before labels. Do not infer ADV63 from a 21-day metric or use entry-day close at decision time.
