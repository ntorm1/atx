# FQ1/FQ2 readiness measurement integration — static audit

Scope: read-only inspection on `feat/tier1-parity`, 2026-09-23. No warehouse, runtime, tests, migrations, or network were used. The codebase graph MCP tools were unavailable in this session, so discovery used `rg` and direct source reads.

## Recommendation

Add an **opt-in, bounded FQ1/FQ2 research inventory** to `atx-db/scripts/measure_tier1_readiness.py`, next to the existing `--include-cf1` path. The JSON key should be `fundamental_signal_research` (with `status: not_requested` by default); its Markdown section should say “Recorded FQ1/FQ2 research evidence.” The overall `certification` remains `unmeasured`, and the section must state that recorded manifest status, hashes, candidate flags and blocker fields are **observations, not read-side digest validation, production eligibility, alpha certification or parity proof**. This belongs in the existing measured artifact and single read-only snapshot, not a new warehouse job.

Exact interface: add `--include-fundamental-signals` and `Measurement.fundamental_signals()`. Call it in the report dictionary where `cf1` is called, render a compact Markdown table (or bounded JSON block) after CF1, and add one measurement limitation about manifest inventory versus the FQ1 validator and FQ2 label digest. Leave `SURFACES` alone: FQ1's high-cardinality `fundamental_signal_values`, `fundamental_signal_inputs` and `fundamental_signal_proofs` are intentionally outside this report. No import of `atx_db` is needed.

## Existing contracts that shape the report

- Migration 0324 (`atx-db/src/atx_db/migrations/bodies_0324.py`) defines `fundamental_signal_runs` (one row/run) and `fundamental_signal_coverage` (one row/run/signal/session). Coverage already stores `status`, member counts, eligible/excluded counts and unmatched-owner counts, including empty sessions. The builder calls a run `complete` when sessions and eligible scores exist; `blocked_empty` and `failed` remain diagnostic. Every run records blockers and `production_eligible=false`.
- `validate_fundamental_signal_panel` in `fundamental_signal_research.py` is the actual FQ1 consumer validation. It verifies manifest hashes, definitions, observed calendar, row grains, clocks, diagnostic counts, blockers and a digest over values, inputs, coverage and proofs. Calling it here would turn measurement into a costly source/calendar revalidation and scan the value tables. Merely reading `panel_sha256` must not be described as verification.
- Migration 0325 (`.../bodies_0325.py`) defines `fundamental_signal_evaluation_runs`, `_summaries`, `_deciles`, and `_label_evidence`. FQ2 first calls the FQ1 validator. Its complete run stores build/sample/result hashes and summary rows for all signals, horizons and splits. Summary `candidate` is a research screen; `production_eligible` is false. Selected labels are digest pinned but not archived or automatically rechecked on read (`atx-db/docs/FUNDAMENTAL_SIGNAL_EVALUATION.md`).
- The readiness script already offers `Measurement.missing()` for schema gaps, `rows()` with a 1,000-row output cap/truncation flag, `one()` for aggregates, `--include-cf1` for optional research inventory, one read-only DuckDB transaction, disabled external access, one thread, bounded spill, exclusive output creation and a report-wide `certification: unmeasured`. Its `safe()` redacts only emails/sensitive keys; it does **not** make arbitrary JSON/text safe for release. Avoid selecting `spec_json`, `definitions_json`, `source_ids_json`, `config_json`, `diagnostic_json`, `annual_json` or unrestricted `blockers_json` into artifacts.

## Bounded query shape

1. Check required columns using `missing()` separately for each surface so a missing FQ2 migration does not suppress FQ1. For FQ1 require run ID, status, dates, panel hash, blockers and production flag; for coverage require run ID, signal ID, date, status, `visible_members`, `common_members`, `overlap_members`, `qualified_cik`, `unmatched_owner_states`, `eligible_scores`, `excluded_scores`, `constant_scores`. For FQ2 require run ID, build ID, status, observation date, run time, build/result hashes, blockers and production flag; for summary require run ID, signal ID, horizon, split, primary flag, status, spread dates, label coverage, eligible/labeled counts, Holm p-value, net 25 bp, candidate and production flag. Report schema gaps as `unmeasured`.
2. For each run table, use a bounded ordered inventory such as `SELECT run_id,status,as_of_date,run_at, ... FROM main.fundamental_signal_runs WHERE as_of_date<=? ORDER BY run_at DESC,run_id DESC` via `rows()`. The 1,000 cap and `truncated` field must remain visible. Keep hash fields as **recorded digests** if useful; never say matched. Record status counts using a single aggregate with fixed status buckets (`complete`, `building`, `blocked_empty`, `failed`, other) and one count of future-dated runs if desired. Do not emit arbitrary diagnostic/error text or source/config JSON. For FQ2 include `build_run_id`, so the relation to the FQ1 manifest is visible; say it is a recorded link only. Select run IDs for detailed reporting from completed runs with `as_of_date<=report date`; an absent complete run is `not_run`, not a zero-quality result.
3. Measure coverage for **one selected completed FQ1 run** (the latest by `run_at,run_id`) by a parameterized `WHERE run_id=?` query grouped by `signal_id,status`, with `count(*) AS sessions`, `min/max(decision_date)`, `sum(eligible_scores)`, `sum(excluded_scores)`, `sum(unmatched_owner_states)`, and counts of `constant_scores`/zero-visible/zero-common sessions. Use `rows()` so grouped output has the same cap and truncation marker. This scans the narrow coverage table for one run; it does not touch per-security values. The selected run's date range and count are inventory facts, not calendar validation. If the run list itself truncates, selection still follows SQL ordering; do not present it as an exhaustive run inventory.
4. For **one selected completed FQ2 run**, read its frozen summary rows using `WHERE s.run_id=?` and a manifest join `JOIN fundamental_signal_evaluation_runs e ON e.run_id=s.run_id AND e.status='complete'` (and, if displayed, `JOIN fundamental_signal_runs b ON b.run_id=e.build_run_id AND b.status='complete'`). Select only `signal_id,horizon_sessions,split,primary_hypothesis,status,spread_dates,eligible_count,labeled_count,label_coverage,holm_p_value,net_25bp,candidate,production_eligible`, ordered by signal/horizon/split, through `rows()`. The nine rows per signal are bounded by the existing cap and truncation field. Display `candidate` as a *recorded research flag*, never as release readiness. A limited status/attrition count from `_deciles` is optional; avoid it in the minimum change because the summary already carries coverage and result status.
5. Expose blockers through a **fixed code allowlist**, not `detail()` or raw JSON. FQ1 known codes are the four `_BLOCKERS` constants plus `no_observed_decision_sessions`, `no_visible_historical_common_membership`, `unmatched_derived_owner_lineage`, `no_eligible_fundamental_signal_scores`; FQ2 has six `_BLOCKERS` constants in `fundamental_signal_evaluation.py`. A helper may select `length(blockers_json)` and at most `left(blockers_json,2048)` for the selected run(s), accept only a full, valid JSON list of distinct allowlisted strings, and return known codes plus `invalid_or_oversized`/`unknown_code_count` without echoing unknown values. If oversized or malformed, report blocker detail `unmeasured`; do not interpret a truncated prefix as complete. This is diagnostic display, not equivalence to the FQ1 validator's canonical blocker check. Simpler initial implementation: report only `blocker_count` plus `blocker_detail: not_inspected`, and let the existing documented fixed blocker list explain categories.

`production_eligible` can be reported as `recorded_production_eligible` with the explicit note that the report does not validate it, but avoiding the field entirely is clearer for the first pass. Never compute or expose a new “ready” boolean from a `complete` status, candidate flag, hash presence or coverage percentage. Preserve the existing read-only connection, transaction, memory limits, output path checks and exclusive file creation. No live data claim can be made until the controller runs this script in its serialized memory guard slot.

## Minimal validation when implementation is authorized

Offline fixture tests can assert: absent 0324/0325 tables become separate schema gaps; empty and non-complete manifests are not promoted to complete evidence; a complete FQ1 run produces bounded coverage without querying `fundamental_signal_values`; FQ2 summaries are restricted to a complete selected evaluation run; truncation is surfaced; arbitrary JSON/unknown blocker strings never appear; Markdown and JSON keep certification unmeasured. The current audit did not execute these tests.
