# Issuer derived ownership: static correctness audit

Read-only review on `feat/tier1-parity`, 2026-09-23. Scope: `api/service.py::issuer_content_range`, `_issuer_owner_ids`, `_issuer_content_rows`, canonical derived producer and DL1 selected refs. No Python, database, tests, network, migrations, or production edits were run.

## Verdict

**The current issuer API does not prove that a returned derived metric's selected operands belong to the requested CIK.** Its owner collision control is useful, but it examines only content-clock-visible `fundamental_fact_revisions` for each `security_id`. The derived publisher reads **all** `fundamental_standardized` rows for that security, without a CIK predicate (`_derived_pit.py:69-86`), and standardized inputs can come from `fundamental_statement_points` or `fundamental_xbrl_metric` (`_standardization_set_based.py:165-260`). Those source rows retain their own CIK; no producer constraint makes their CIK set equal to the visible fact-revision CIK set at an arbitrary historical `content_as_of`. An owner ID is a partition key, not selected-leaf ownership proof.

`_issuer_owner_ids` selects owners with a requested-CIK fact revision and collects every **visible fact-revision** CIK on those owners (`service.py:473-498`). `issuer_content_range` admits derived owners only when that set is exactly the requested CIK (`:555-559`). `_issuer_content_rows` then filters derived rows by `security_id` and content clock, but has no row CIK predicate and projects the requested CIK as a literal when that field is requested (`:585-653`). Thus a foreign derived row admitted through an incomplete owner set is also labeled with the requested CIK. The focused collision fixture (`tests/test_issuer_content_query.py:123-142`) covers a foreign CIK **with** a visible fact revision, so it does not exercise this gap.

This is a selected-operand issue, not a claim that the absence of a DL1 call is itself defective. The concrete missing invariant is `selected standardized leaf CIK = requested CIK`. `inputs_hash` fingerprints the candidate frame and cannot supply that proof. DL1's retained direct refs and `qualify_selected_lineage` are the available bounded route for reconstructed rows; its reader verifies selected standardized IDs/CIKs, dependency refs and hashes, source/definition, clocks and limits (`derived_lineage.py:105-350`). Old rows with NULL refs remain `legacy_unverifiable` and must not be silently certified. The issuer catalog currently exposes `derived_value_id` only on the separate fundamentals schema, not the issuer derived projection (`api/catalog.py:951-966`), so a serving integration needs an internal ID for qualification before projecting requested fields.

## Smallest counterexample

The following is a **synthetic row sequence**, not an observed production CVX row. Let A be CVX CIK `0000093410`, B another CIK, O one reused accounting owner, and cutoff `2026-09-20 22:00:00`.

1. `fundamental_fact_revisions` contains `(security_id=O, cik=A, available_at=2026-01-01, as_of_date=2026-01-01)`. It contains no B row visible at the cutoff. A B fact row may exist with `available_at=2026-12-01`; the historical query still cannot see it.
2. `fundamental_statement_points` or `fundamental_xbrl_metric` contains valid B quarterly diluted-EPS inputs under `security_id=O`, `cik=B`, with availability before the cutoff. Standardization retains B on the selected state. For the release-backed EPS path specifically, a later B Company Facts row can establish the unique B owner during a later refresh while the B release's older availability remains the standardized event clock (`reported_eps_core.py:59-120`).
3. The canonical derived refresh processes O as one security scope, selects B's standardized EPS state(s), and publishes a valid `eps_diluted_q_growth_yoy/q` row under O with `available_at <= cutoff` and selected leaf refs carrying B. There is no CIK filter in `_derived_pit.prepare_security`.
4. `issuer_content_range(cik=A, schema_name='derived-metrics', items=['eps_diluted_q_growth_yoy'], basis=['q'], content_as_of=cutoff, ...)` computes `owner_map[O] == (A,)`, includes O in `derived_owners`, and returns B's derived row. If `cik` is requested, it returns literal A beside B's metric. Revision ranking and the period filter do not correct ownership.

The schema-level minimum for the API mistake is one visible A fact-revision row and one visible B-derived row sharing O. The producer-consistent sequence above adds actual B standardized leaves and source rows; it does not require an impossible B fact-revision row to be visible at the historical cutoff.

## Bounded correction

Keep the existing owner discovery and collision metadata as a coarse filter. For derived rows, select a bounded page of candidates with their internal `derived_value_id`, then run `qualify_selected_lineage` in bounded batches using the requested normalized CIK, the content cutoff, and approved metric/window definition hashes. Include a numeric row only when its result is `qualified`; report rejected or legacy rows with an explicit ownership/lineage status rather than labeling them A. Apply the public `limit` **after** qualification (with bounded scanning/pagination) so rejected rows do not hide valid quarters. Do not use the returned literal `cik`, `security_id`, or candidate-frame `inputs_hash` as substitute proof.

For an unavailable/NULL revision, preserve the event in the visible quarter history and report its `value_status` plus an explicit lineage qualification outcome. DL1 currently returns `invalid` for missing selected operands or invalid values, even if present leaves have the expected CIK (`derived_lineage.py:234-350`); that is not `qualified` numeric ownership. A serving rule for unavailable events should fail closed on any foreign selected leaf, surface legacy/unverifiable states distinctly, and avoid claiming full operand ownership where a required input has no identity. This keeps the desk's requested unavailable revisions visible without presenting a foreign numeric metric as CVX's.

The API's revision selection already ranks content-clock-visible states before the period range and retains the latest NULL state (`service.py:639-653`), as the focused test shows. The first three requested quarters and their values still depend on production activation/source coverage; this static audit does not claim a live CVX result or measured lineage qualification.
