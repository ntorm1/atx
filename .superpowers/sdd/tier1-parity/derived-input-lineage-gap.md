# Derived metric selected-input lineage gap

Read-only audit, 2026-09-23. Scope: the canonical quarterly `derived_metric_values` publisher and its consumers. No database execution or schema reservation.

## Finding

`derived_metric_values.inputs_hash` is an integrity fingerprint, not an invertible operand map. In `_derived_pit.py::prepare_security`, `_pit_raw` reads `standardized_id` but drops `fundamental_standardized.cik`. `_pit_items` and `_derived_annual.py::prepare_security` then hold the selected standardized `state_id`, period, source, rule and clock in temporary structs. `_derived_pit.py::frame_sql` assembles per-bucket `base.lineage` from those structs and dependency states; `hashed` folds that lineage into `inputs_hash` but inserts only the hash through `STATE_COLUMNS`. `finish_metric` and `derived_metrics.py::refresh_derived_metrics` publish only those columns, then cleanup destroys the temporary inputs and frame. A dependency's temporary lineage is just its `derived_value_id` plus its own opaque hash, not its source leaves.

The surviving source tables do contain `fundamental_standardized.standardized_id` and `cik`, and some other accounting surfaces have their own `input_*_ids_json`. The issuer-content API (`api/service.py::_issuer_content_rows`) can fetch a *derived* state and qualify a source owner for the queried CIK, but it cannot prove which standardized leaves generated that derived state. `asof/fundamentals.py::issuer_derived_asof` and `derived_factor_projection.py::load_projection_inputs` also expose the state ID/hash without reconstructing leaves. `v_metric_lineage` is a separate legacy/other-surface view, not a stored inverse of the canonical derived hash. The four-metric desk screen's EPS owner reconstruction is a hand-built, metric-specific approximation; its own comment correctly calls `inputs_hash` opaque.

There is a second trap: the current `base.lineage` includes *candidate* input states across every frame bucket and annual alternative. It does not mark the winning `annual_fallback`/weighted-share choice or a `coalesce` branch. Persisting that JSON unchanged would make a broader audit possible but would **not** establish the exact operands used in the numeric result. Hash matching cannot tell which candidate CIK to qualify. An old row with no new lineage must remain `unverified`, never be assumed to have same-CIK leaves.

## Smallest generic persistence fix

Add one nullable `selected_input_refs_json` column to `derived_metric_values` in the next **unreserved** migration after FQ1's 0323 (do not assign a version until coordinated). Each rebuilt `event_reconstructed` row stores a stable, ordered JSON array of its **direct** selected operands. Each element has `kind` (`item` or `metric`), code, frame bucket/offset, selected state ID (`standardized_id` or `derived_value_id`), selected availability, and for `item` the selected CIK, basis, source and fiscal span. Include an explicit missing operand element/status when arithmetic is NULL. A `metric` ref points to its dependency row; consumers recursively follow that row's refs to standardized leaves, rejecting a missing/cyclic/legacy edge. This avoids copying a transitive tree into every descendant row and avoids a separate high-cardinality edge table and index. It does not certify historical delivery vintages; it makes selected source ownership auditable under the existing modeled clock policy.

Required edits, bounded to canonical publisher and readers:

1. New migration body/registry entry: add nullable `selected_input_refs_json VARCHAR`, update table/field catalog with JSON semantics, and leave preexisting rows NULL as uncertified. No backfill by guessing from hashes. FQ1 owns 0323; coordinate the next free number.
2. `_derived_pit.py::prepare_security` and `_derived_annual.py::prepare_security`: retain `cik` and selected `state_id` in item/annual structs. `_derived_pit.py::prepare_metric` carries a dependency's selected state ID (already present), with refs available for recursive audit.
3. `derived_dsl.py` plus `_derived_pit.py::frame_sql` / `_derived_annual.py::frame_annual_columns`: emit a provenance expression alongside numeric lowering. A `Ref` yields its direct selected state; arithmetic joins operand refs; `lag`/`yoy`/`ttm`/averages select the exact frame offsets; `coalesce` selects the same branch as value SQL; annual alternative and weighted-share choices use the already-computed branch predicates. Deduplicate only identical `(kind, state_id, bucket, role)` refs, preserving deterministic order. Define NULL/missing and literal-only behavior explicitly. The existing full-frame `inputs_hash` need not change, because it still fingerprints candidate states; selected refs are a separate contract.
4. `_derived_pit.py::STATE_COLUMNS`, `frame_sql`, `finish_metric`, and `derived_metrics.py::refresh_derived_metrics`: carry the JSON through `_pit_metric`/`_pit_stage` and the same per-security transaction as the metric rows. Compression must compare selected refs too so a lineage-only transition cannot disappear. Keep existing per-security input, candidate, frame and publication limits; add a serialized-ref byte/count cap per output row and fail the security scope before DELETE if exceeded. Memory remains one SQL chunk/security; no Python fact-panel collection.
5. `asof/fundamentals.py::issuer_derived_asof` and `api/catalog.py::ISSUER_DERIVED_SCHEMA` (service projection is catalog-driven): expose the stored refs. Add a small read-only resolver in a new `derived_lineage.py` used by the future generic signal panel, with bounded recursion/visited IDs. It must check every *selected* leaf's `cik` against the uniquely dated decision-time identifier CIK, and that each dependency row is itself visible at the decision cutoff, has reconstructed history/definition, and carries refs. Return explicit `qualified`, `mismatch`, `missing`, `ambiguous`, or `legacy_unverifiable`, with leaf IDs, rather than inferring success from `security_id` or `inputs_hash`. API can expose raw refs first; no extra issuer endpoint is required for the persistence fix.

Focused proof obligations: fixture with a direct item, nested derived metric, `ttm`/lag input, annual fallback, unused annual candidate, `coalesce` winning branch, same-value source-state change, NULL invalidation and cross-CIK source row. Assert persisted refs are the operands used (not all visible candidates), recursive CIK qualification rejects the cross-owner path, serialization and hash are deterministic across chunk sizes, old NULL refs fail closed, and a failed scope keeps old metric rows. These tests should run on temporary DuckDB only.

**Immediate caller implication:** FQ1's daily signal panel should not label a derived value issuer-qualified until this persistence/rebuild exists. It may keep the row as `lineage_unverified` and report coverage. The exact source leaves are not reconstructible from currently published `inputs_hash`, so no current historical performance claim may silently treat that hash as CIK proof.
