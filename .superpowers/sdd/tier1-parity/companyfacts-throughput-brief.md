# Companyfacts archive throughput: bounded follow-up

Static design review, 2026-09-20, updated to the implementation scope authorized by the controller. No imports, tests, database connections, runtime probes, or live-job operations were performed by this agent. Graph tools were unavailable in the exposed catalog; source discovery used text reads. Runtime ownership remains with the root controller. Implementation status is recorded in `companyfacts-throughput-report.md`.

## Evidence and decision

Controller observations after OOM repair `a5004bf5`: archive2 started at 19:39:07; 25 targets were processed at 19:40:29 with 147,049 inserted rows; 50 at 19:41:34 with 259,949 rows (40 loaded, nine empty, one failed), out of 20,390 targets. The second 25-target interval took 65 seconds, or 2.6 seconds per target across the whole loop. These observations do **not** identify operator timings or establish a full-archive completion estimate.

The authorized follow-up in `fundamentals.py` inventories exact existing raw CIK spellings once per load, then uses direct parameterized CIK predicates for old-key staging and raw deletion. Preserve the transaction and exact point-deletion relation from the OOM repair. No persistent schema/index, registry, activation, or job changes; no archive-wide fact materialization or shadow rewrite. The point-ID prefilter considered below is deferred.

## Raw-fact selection

Current `_replace_facts` stages old keys at lines 1210-1216 and deletes raw facts at 1258-1259 using `regexp_full_match(trim(cik), '[0-9]+') AND try_cast(cik AS BIGINT) = cast(? AS BIGINT)`. Both statements must evaluate a computed CIK predicate over their candidate history for every issuer. A direct stored-column predicate makes storage pruning possible and removes repeated normalization work; actual pruning remains unmeasured.

1. Add a private inventory helper returning `dict[int, tuple[str, ...]]`. Query only distinct raw `sec_company_facts.cik` values, and derive their numeric keys in SQL using **exactly** the existing regexp/trim and `try_cast(... AS BIGINT)` rules. Drop NULL numeric keys. Retain each original string verbatim, including spaces and extra leading zeros. Do not substitute Python `strip`/`isdigit`/`int` validation, which can accept a different language of strings. No fact keys, IDs, or rows enter this global Python inventory.
2. Create the inventory as a local variable of `load`, once before the first successful member replacement, and reuse it across that load's targets. Lazy creation avoids work for empty windows or runs containing only source failures. This can serve all selector modes through the common load path; it is not an archive-only side path.
3. Add an optional keyword argument to `_replace_facts`, such as `stored_cik_spellings: tuple[str, ...] | None = None`. `None` retains the current guarded predicate for independent callers. The loader supplies the complete alias tuple for the numeric target. Build `cik IN (?, ...)` with bound string parameters for **both** old-key staging and raw deletion. An empty tuple becomes `FALSE`, preserving an empty typed key relation and avoiding invalid `IN ()`. Never cap/truncate aliases, and never assume padded plus unpadded spellings exhaust the stored variants.
4. After `_replace_facts` commits successfully, add the inserted canonical CIK to the local inventory if facts were nonempty. Keeping deleted aliases as harmless supersets is simpler than mutating them away. Empty replacements add nothing; failed source members and failed SQL transactions do not mutate the inventory. The loader supplies canonical CIKs to normalization, so its inserted spelling is known. Independent callers can still insert arbitrary spellings and retain fresh predicate evaluation through the default path.

Memory scales with distinct raw CIK spellings, not 31.6 million fact rows. The controller reports 6,533 existing distinct raw CIKs. Use SQL DISTINCT before fetching. This is not a universal fixed-memory bound: pathological spelling cardinality could be large. A temporary SQL inventory is the fallback if measured cardinality/guard results reject the dictionary; it retains SQL spill capability and fetches only one issuer's aliases at a time, at the cost of lifecycle code and one extra query per issuer. Do not introduce both implementations now.

The inventory is valid for the loader's serial writer path: it observes existing spellings, and the same path maintains its own successful inserts. Never retain it on a dataset/store object across loads. Rebuild on a new load/retry so external changes between calls are visible. Supporting concurrent independent writers during the loop would require a different synchronization contract; a silently stale persistent cache is not acceptable.

## Point and smaller-table filters

The repaired `DELETE FROM fundamental_points ... USING companyfacts_point_delete_keys` already preserves exact identity/key ownership and remains unchanged in this patch. A later redundant direct `p.security_id IN (?, ...)` filter could use only distinct IDs from the issuer's final deletion-key relation, retaining the join, source filter and six NULL-safe key comparisons. That set necessarily includes every matching ID, so its use as a redundant prefilter is equivalent; IDs alone would not be sufficient deletion evidence. The join may already provide equivalent runtime filtering. Defer that change until production evidence separates its benefit from the raw-CIK improvement.

Leave the guarded CIK predicates in `sec_company_tickers` legacy-ID discovery (1225-1227) and scoped candidate cleanup (1262-1266) intact for this patch. Raw-fact aliases cannot safely filter either table: each may contain a spelling absent from raw facts. Their inventories could be separate later if evidence warrants it. Do not alter PIT resolution or its historical availability predicates.

## Existing unresolved-candidate accumulation

`resolve_company_facts_identifiers` drops duplicates by CIK before returning its unresolved frame. The archive loop accumulates those reduced frames and concatenates them after the loop. Since archive targets are deduplicated by CIK, accumulated row count scales with target count (20,390 here), not fact history. There is one small DataFrame object's overhead per unresolved issuer and a concat-time copy; the resolver also temporarily builds unresolved rows for the current issuer. This is a concrete cardinality/object-overhead concern, not evidence of an archive-wide fact-row memory leak. Leave it unchanged. If guard measurements identify material overhead, a separate small change could accumulate issuer summary records while preserving existing counts and representative candidate fields.
